# 对账类功能如何测试：先把业务关系说清楚

对账功能的难点不只是比较两个金额，而是要说明一条业务记录为什么能匹配、为什么不能匹配，以及异常记录后续怎么处理。

我会先确认匹配主键，例如订单号、退款单号、门店和交易日期，再分别准备正向记录、退款记录、重复导入和金额不一致的数据。测试结果不能只看页面显示的总数，还要抽查明细，确认原始记录没有被误删，关联状态和异常分类也正确。

几个容易遗漏的场景包括：一笔订单多次退款、退款金额超过正向金额、同一批文件重复导入、两边记录时间跨天，以及字段为空或格式不一致。这些场景不一定都要在第一轮上线前解决，但应该被记录并和产品确认处理规则。

这个项目的用例生成器会针对“对账、退款、核销”补充匹配、边界、一致性和重复导入场景。生成器能帮助我减少遗漏，但不能替代业务判断。比如“重复导入是否去重”必须以产品规则为准，而不是凭测试人员猜测。

## 我会核对的结果

- 总记录数是否符合源数据？
- 匹配成功、未匹配和异常记录的数量是否能解释？
- 金额合计是否一致，退款是否被重复计算？
- 重复导入后是否产生重复业务记录？
- 页面结果、导出文件和接口返回是否一致？
