# 从接口检查到页面检查：先快后全

页面测试能模拟真实用户，但启动浏览器、等待页面加载和定位元素都需要时间。接口检查更快，适合先确认服务是否可用、状态码是否正确，再用页面测试验证关键用户流程。

我的基本顺序是：先做轻量的接口或健康检查，再做页面上的核心路径，最后补充兼容性和视觉细节。这样失败时更容易判断问题大致在服务、数据还是页面交互。

项目中的 `platform_checks.py` 提供了一个简单的 `check_url` 函数，统一返回是否通过、状态码、耗时和响应类型。统一结果格式的好处是，命令行测试、Streamlit 页面和 CSV 报告都可以复用同一份结果。

页面测试则关注用户真正能看到的行为，例如输入账号密码、点击登录、检查跳转地址和关键文本。页面测试不应该把每个样式细节都写成强约束，否则页面正常改版也会造成大量无意义失败。

我会把接口测试和 UI 测试当成两层互相补充的检查：接口层发现服务契约和数据问题，UI 层确认用户流程是否可用。两层都失败时，优先检查服务和环境；只有 UI 失败时，再看定位器、加载时机和页面状态。

## 一次回归前的快速顺序

1. 检查测试环境地址是否可访问。
2. 执行接口和页面的关键路径检查。
3. 保存失败响应、截图或页面文本，保证问题可复现。
4. 再补充浏览器、分辨率和异常网络场景。
