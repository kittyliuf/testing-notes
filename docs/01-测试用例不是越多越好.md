# 测试用例不是越多越好：我会先找风险

刚开始写测试时，很容易把需求中的每一句话都改写成一条用例。这样看起来很完整，但执行成本会越来越高，真正重要的风险反而不容易被发现。

我现在会先问三个问题：这个功能最可能在哪里出错？出错后影响多大？用户能不能在页面上发现问题？答案通常会引导我优先覆盖四类场景：正常流程、边界值、异常输入和重复操作。

以登录功能为例，除了正确账号密码，还需要考虑空值、错误密码、字段长度边界、特殊字符、连续失败，以及登录后是否真的跳转到正确页面。每条用例都应该有清晰的预期结果，例如“提示账号或密码错误”，而不是只写“登录失败”。

在这个项目中，`build_cases` 会根据需求关键词补充边界、异常、权限和兼容性检查。这只是生成初稿，最终仍需要测试人员结合业务确认：哪些规则是真实存在的，哪些场景优先级更高。

我的经验是，好的测试用例不在于数量多，而在于能解释覆盖了什么风险、为什么值得执行。用例执行后还要记录失败现象、复现步骤和影响范围，这些信息比单纯的“通过/失败”更有价值。

## 我会保留的检查清单

- 正常路径是否能完成核心目标？
- 输入的最小值、最大值和空值是否符合规则？
- 网络中断、重复点击、重复提交会发生什么？
- 不同角色是否只能看到和操作有权限的内容？
- 失败时是否有明确提示，且没有保存脏数据？
